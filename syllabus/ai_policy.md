# Generative AI / LLM Policy

Spatial Programming (GEOG 49076 / 59076 / 79076)

There is some irony of teaching a modern spatial *programming* course and placing limits on the use of AI coding tools, as that is how much professional code now gets written. But using those tools well requires exactly kinds of skills this course exists to build - reading, writing, and reasoning about code yourself. Simply put, you are unable to verify, test, or catch the errors in generated code you couldn't have written. If a model writes code *for* you before you can read it, you leave this course without learning much. That said, coding with AI assistants (and assistance) is here to stay, and I would be doing your careers a disservice not to acknowledge that fact. Accordingly, we will discuss the use of these tools later in semester, after we have covered the fundamentals - especially the spatial ones.

**TL;DR version: AI tools do not write your code (or your prose) in this course, unless an assignment expressly says otherwise. Any permitted use must be disclosed, justified, and explainable. Practicum days are fully unplugged. When you're not sure, ask first.**

---

## Prohibited uses

Under Kent State's academic integrity policy ([3-01.8](https://www.kent.edu/policyreg/administrative-policy-regarding-student-cheating-and-plagiarism)), using generative AI on coursework where it is not expressly permitted is **cheating**. In this course, that specifically includes:

1. **AI-generated code.** Using any generative AI tool (ChatGPT, Claude, Gemini, GitHub Copilot, Colab's built-in AI features, or any LLM-powered completion or chat tool) to generate, complete, translate, or fix code you submit. *Instead:* the library documentation linked in each week's readings, your own course notebooks, office hours, and classmates within the collaboration policy. Both Colab and VS Code ship with AI assistance turned **on**, and part of week 8's setup (see the account setup guide) is turning it off for coursework.
2. **AI-debugged code.** Pasting your assignment code into an AI tool to have it find or fix the problem. Debugging *is* a skill — a large share of programming is exactly this. *Instead:* read the traceback bottom-up (week 5), talk it through with a partner, bring it to office hours.
3. **AI-written prose.** Copy-pasting AI-generated text into write-ups, interpretation sections, peer reviews, or graduate memos — including text you edited afterward. Your peer reviews and interpretations are where I hear *you* think. *Instead:* the [Writing Commons](https://www.kent.edu/writingcommons); grammar tools are fine when constrained to grammar and concision.
4. **Uploading course materials.** Putting course datasets, lab briefs, template notebooks, slides, or readings into AI platforms for summarization, explanation, or completion. Course materials are intellectual property, and uploading an assignment to have it explained is mostly a way to skip the part where you learn it. *Instead:* ask me, do the readings, or talk each other.
5. **Any AI use on practicum days.** No AI-generated code, completions, or *explanations* on either day of either practicum, from any tool. Practicums are the recital: the point is finding out what you can build on your own. (See the practicum briefs.)

## Permitted uses (no permission needed)

Used this way, these tools function something like an on-call tutor:

- **Concept clarification**, with course materials kept out of the conversation. For example, "explain what a coordinate reference system transform actually does," not "explain what this lab is asking."
- **Finding sources**: asking for pointers to documentation, journal articles, or tutorials beyond the course readings (then verifying they exist and say what the tool claims).
- **Software and setup troubleshooting**: ArcGIS Pro licensing snags, Colab connection issues, git and GitHub setup. This refers to the tooling around your work, not the work itself.

## Expressly permitted uses (assignment-specific)

Some assignments and designated parts of later Part 2 tasks will **expressly permit** AI for specific steps. If assignment instructions do not explicitly allow for the use of AI, the default rules above apply. Where AI use is permitted and you use it, you MUST fulfill two requirements:

- **Disclose and justify.** Your submission must include a brief AI-use statement: which tool you used, what you asked it, what you kept or changed, and why AI was appropriate for that step. "It wrote my code" is not a justification; "I used it to generate boilerplate for X, then verified Y and corrected Z" is.
- **Be able to explain everything you submit.** I may ask you to walk me through any part of your work. Code you cannot explain is treated as work that is not your own, whatever its origin.

## Worth thinking about

Beyond the rules, part of using these tools professionally is deciding where you stand on them. Some issues worth sitting with, in a course about spatial data specifically:

- The energy and water footprint of the infrastructure behind every prompt
- Where training data comes from, who consented to its collection, and what that means for data sovereignty — including Indigenous data sovereignty, a live issue in geography
- The labor conditions of the data-annotation work (which largely takes place in the Global South) that made these models possible
- What outsourcing your thinking does to your own learning
- Hallucination: plausible-but-wrong code produces plausible-but-wrong maps, and maps can be used in decision-making
- What is lost when you ask a chatbot instead of a classmate

We will come back to these later in the semester.

## Questions

If you are ever unsure whether a use is allowed, ask *before* you use it — that question is always welcome, and asking it is itself good professional practice.
